Chapter 3: The encoder

Now, I’m going to be completely honest, just making the encoder function properly took like a month because of a few things.

Issue 1: Encoder kept disconnecting

  • Fix: use better and tighter wires

Issue 2: Wires will come loose due to vibrations from motor

  • FIx: use hot glue to secure wires

Issue 3: wires too long because the AS5600 uses I2C

  • Fix: use pull-up resistors (calculated to be around 3.3k ohms)

Issue 4: motor makes a lot of electrical noise

  • Separate rails and add a low pass filter (use a capacitor)

Issue 5: Encoder disconnected which would brick my arduino

  • Fix: catch the errors early

Issue 6: wires too long for I2C

  • Fix: Decrease pull up resistor resistance and decrease length wherever possible

Issue 7: stepper motor produces a lot of EMI that could corrupt the signal along the way or give false readings

  • Fix: coil wires and pray (it worked)

After all these issues, I could actually read the data and perform some action that could make it stay upright

Chapter 6: the PID

Now that I had all the parts built and assembled and I knew which way was up, I could actually start implementing code that could balance it.

Now, you’re probably asking yourself, why did you choose PID and not some other feedback algorithm? The main reason was because PID is really easy to implement and simple to find the parameters. Not the best parameters but parameters that generally are good enough for my situation.

  • Other algorithms like LQR or FSF require models to actually calculate the best possible solution. And it would be basically impossible to just guess and check it and my setup has so many uncertainties that would be annoying to address. If I was doing something more precise like a double pendulum (for example), a more accurate algorithm might be better than guessing and checking. But in my case, PID was good enough for me.

TLDR: I can guess and check PID which is good because I basically threw together my setup.

So turns out 1 PID controller was not enough to balance it. It could stand upright and move fine, but it would drift off to 1 side all the time no matter what I did.

Quick Example

At this point in time, I did some research and I discovered the cascade PID.

  • Basically how it functions is that there’s 2 PID loops. In my case, a slower outer one would try and bring it back to the center of the belt, while the faster inner one would just keep it upright.
  • The outer one checks where the cart is on the belt and uses that value for its PID
  • The inner one checks the angle of the pendulum and uses that angle for its PID
Example

How it would function is that the outer PID would give it a “target position/angle” from the position of the cart. Then from the values P, I and D, it would calculate a good target angle for the inner PID.

Then the inner PID would look at its actual angle and then look at the target angle and using its P, I and D (different from outer PID values), it would calculate a suitable speed for the motor to move at.

In the picture above, at that exact moment in time, it would calculate a signal for the cart to move left to get the target angle.

To find the position of the cart, I just counted the steps of the motor and the PID took care of the rest. For example, if I took 650 steps, I know I would probably be at the other side so that means that if I took 325 steps in the opposite direction, I would be at the center.

  • I know that counting steps is dangerous because the motor can easily slip or I miss a step. However, it's very easy to implement and raising the current that I gave the motor compensated for most of the issues. (I’m not worried about power or heat)

Chapter 3 stuff

If you’re wondering why an entire chapter was given to the encoder, it was because I spent like 2-3 weeks debugging why the encoder was giving bad values. I also had to learn what I2C (inter integrated circuit) was.

Just a side note: the encoder I was using (AS5600) could provide analog outputs that I could read but the main issue is that it would lose 4 times the resolution and I need it to be pretty precise. After finishing it, I think analog might have been easier to use but you know what they say, the journey is more importanter than the destination.

If you’ve seen my final code, you know that I used this library wire.h to handle I2C. And you might be asking yourself, why didn’t you just write it yourself? And the reason was because I could produce something 10x worse at 10x the time spent.

If you’re asking how I found the pull-up resistors value, it's mainly just v = ir but with extra steps and those extra steps you can figure it out yourself. This video explains it really well.

  • Basically, there's a minimum resistance and it's calculated by how much current the actual component can handle. For my AS5600, it's around 0.003A or 3mA. Therefore by using the 5V pin, it's around 1.5 kOhms. Rmin = (VDD - VOLl) / IOL = (5 - 0.4) / 0.003 ~=~ 1500 ohms
  • Now why do you even need pull-up resistors? It's mainly because when the arduino needs to communicate with chips, they both only pull the SDA/SCL lines to GND (because if one side was high and the other was low, there would be a short). Since they can only pull it down, pull-up resistors are required to literally pull up the voltage if neither device is currently pulling it down.

    Note: pull-up resistors don’t short the circuit when a line goes LOW because they limit the current. If the resistance is too low, too much current flows into the pin, exceeding its maximum sink current (IOL) and preventing the line from dropping down to a valid LOW voltage (VOL)—which is why there is a minimum resistance requirement.

  • Now most peripherals know this, and they have built in pull-up resistors. Mine has 10 kOhms of resistance that's connected to the VDD. In my case, 10 kOhms of resistance is a bit too high for me and I needed to lower it.

    (Note: 10 kOhms is too high because of interference from my stepper motor and the length of the wire that I was using. Longer wires means larger parasitic capacitance and a longer tau/time constant to pull up the voltage. Therefore, we need to lower the pull-up resistance to decrease tau.)

  • To lower it, I can add more resistors in parallel to lower the Req and as a result,it would pull the voltage up faster. This is achieved by just adding resistors externally because now the built in resistors and my external resistors are both pulling it up now. By pulling it up faster, I can send signals faster which is always a good thing.
  • Now you might be asking? How did I calculate the value of Req (like how did I know it was supposed to be around 3.3 kOhms)? Well … I didn’t. I first tried an Req of 5 kOhms which didn’t work so I lowered it further and 3.3 kOhms worked quite well.
  • Now you might be wondering, what if we don’t use pull-up resistors? Well, there would be an error/timeout flag that would be infinitely blocking and brick my arduino.

    (Technically I could catch it and prevent the flag, but that would block stepper_name.runSpeed() and the rod would fall in that time. So it's better to avoid it in the first place). So I had to include pull-up resistors without breaking everything.

TLDR: guessed and checked 3.3 kOhm pull up resistors. If I didn’t use pull-up resistors, bad things would happen

Chapter 5 stuff

Initially, to see if the rod had settled I just checked if the previous position of the rod matched the current position of the rod every few seconds. Now obviously that doesn’t work because turns out pendulums have a constant period and I was also checking at a constant period. At some point, they’ll have a LCM and give a false positive. This is easily fixed by adding a counter that forces it to match multiple times in a row.
